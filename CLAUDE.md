Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 · shadcn/ui ·
Drizzle ORM · Postgres · better-auth · AWS S3 · Zustand · exceljs · Vitest · Playwright.

## Architecture

### Routing & access control
- `src/app/(app)/*` — authenticated app shell (sidebar + topbar in `(app)/layout.tsx`); the layout calls `auth.api.getSession` and redirects to `/sign-in` if missing.
- `src/app/(auth)/*` — sign-in, `/forgot-password` and `/reset-password`. Public registration is intentionally disabled (`emailAndPassword.disableSignUp: true`); users are created from `/users` by an admin.
- `src/app/api/*` — route handlers (e.g. `api/auth/[...all]` for better-auth, `api/exports/[id]/download` rebuilds an export on the fly).
- `src/proxy.ts` (Next 16's renamed middleware) gates protected paths (`/dashboard`, `/my-work`, `/builder`, `/preview`, `/catalog`, `/vendors`, `/approvals`, `/history`, `/users`, `/audit`, `/projects`, `/settings`, `/drawings`, `/reports`, `/help`) with a real `auth.api.getSession` check, not just cookie presence. It also sends viewers from `/builder/*` to the matching `/preview/*` page, from `/catalog`, `/vendors` and `/history` to `/dashboard`, and from `/projects/[id]/history|diff` to the project page.

### Single-tenant access control
The app ships as a single workspace; `organizations` and `memberships` do not exist. Authorization is driven by `user.role` — `admin | member | viewer` (`owner` was merged into `admin` in migration 0021; `viewer` added in 0022). `src/lib/roles.ts` has `roleOf()` / `isAdmin()` / `canEdit()` and `EDITOR_ROLES` (client-safe; use them instead of casting `session.user`). `src/server/auth-context.ts` exposes:
- `requireSession()` — throws `UNAUTHENTICATED` when no session, `USER_DISABLED` for soft-disabled users.
- `requireRole(...roles)` — wraps `requireSession()` and throws `FORBIDDEN` unless the caller's role is one of the given values. Use `requireRole("admin")` for admin-only flows (tests mock only `requireSession`/`requireRole`, so don't add other helpers there).

**Admin-only:** `/users` (create, role change, disable, password reset), `/audit`, all of Settings except Profile (procurement email, drawing email recipients, reminders, disciplines — including the per-project recipient lists), and deleting/archiving projects, BOMs, vendors and drawings (deleting a BOM needs a reason — `deleteBom({ reason })` puts it in the `bom.deleted` audit summary and payload). Members can create and edit everything else. `{ ok, error }`-style actions return `ADMIN_ONLY_ERROR`; throwing actions use `requireRole("admin")`. Hide the matching buttons for members too (pages pass `canDelete` / `readOnly`).

**Viewers are read-only and get a status-only app** (site managers, PMs checking progress, often on a phone). `/dashboard` renders `ViewerOverview` (`src/components/overview/`) instead of the working dashboard: revisions issued to them to confirm, drawing progress, what waits for approval, what was sent (drawing issues + BOMs to procurement, `src/server/queries/status-overview.ts`) and what's coming up. Their nav (`nav-config.ts`, `VIEWER_MOBILE_TABS`) is Overview, My work, Projects, Drawings and Sent; the builder, preview index, history, catalog and vendors are hidden and redirected in `src/proxy.ts`. On drawing pages they don't see hours or BOM usage, project pages hide notification settings, and search covers projects and drawings only. They can download exports/reports and change their own password, but nothing else. Every mutating action must reject them — throwing actions use `requireRole(...EDITOR_ROLES)`, `{ ok, error }` actions return `READ_ONLY_ERROR` when `!canEdit(session.user)`. The only exceptions are `acknowledgeTransmittal` (a recipient confirming receipt) and `markMyWorkSeen` (their own read marker). Pages compute `readOnly = !canEdit(session.user)` and hide write controls; links into the builder go to `/preview/...` for viewers. Viewers can't be a drawing owner or approving engineer (filter `listOwnerCandidates()` by `role`), but can be a project manager or a notification/transmittal recipient.

**Passwords:** everyone changes their own in Settings → Profile (`authClient.changePassword`). Admins who forget theirs use `/forgot-password` (better-auth `sendResetPassword` only emails admins; members are refused silently). Admins reset members with a temporary password (`resetUserPassword`), which revokes the member's sessions. Passwords an admin sets (new account or reset) are temporary: `user.mustChangePassword` is set and `src/proxy.ts` keeps the user on `/settings/profile` until they pick their own (cleared in the `/change-password` hook and `onPasswordReset`). New passwords need `PASSWORD_MIN_LENGTH` (12, `src/lib/password-policy.ts`). Sign-in is rate-limited per IP keyed on `X-Real-IP` (Railway's edge sets it; `X-Forwarded-For` is client-controlled — `clientInfo()` uses the same order) and locked per email after 10 failures in 15 minutes (`src/server/lib/sign-in-lockout.ts`, counted from `auth.signin.failed` audit rows). Disabled users can't start a session (`databaseHooks.session.create.before`).

**All server actions and queries must call `requireSession()` (or `requireRole(...)` for admin-only flows) before reading or mutating data.** Domain rows are global to the install; do NOT add an `organizationId` column or filter. The root user is seeded by `npm run db:seed` from the constants in `src/db/seed.ts` (`ROOT_USER_*` in `src/lib/env.ts` are validated but nothing reads them yet).

### Data layer
- `src/db/client.ts` — single `postgres-js` pool, exported as `db`.
- `src/db/schema/*.ts` — one Drizzle schema file per table; `src/db/schema/index.ts` re-exports everything. Drizzle config is `strict: true` (see `drizzle.config.ts`) — schema changes require a generated migration.
- Domain model: `user` (with `role`); `projects` → `bomRevisions` → `bomSections` → `bomLines` (lines reference `items` which reference `vendors`/`categories`); `bomExports`, `approvals`, and `auditLog` track artifacts and history.
- Project codes follow the drawing standard (NAMING §4.2): two-digit year + three letters from the name, `26TGT` (`src/lib/codes.ts` `projectCodeLetters` — first letter of the first word and its consonants, Georgian transliterated, company forms like შპს skipped; `PROJECT_CODE_RE`). The New project dialog suggests both parts and the creator may change them; `checkProjectCode` says whether the code is free and offers an alternative, `createProject({ codeYear, codeLetters })` re-checks under the advisory lock (`src/server/lib/codes.ts` `isProjectCodeTaken` / `freeProjectCode`). Codes are never reused — archived projects count, and standard codes have a partial unique index `project_code_std_uq`. Afterwards only an admin changes the code, through `saveProjectPassport({ code })` (audited as `project.code.changed`); stored PDF keys and old BOM export names keep the old code. Old-style codes (`BS-005`) stay valid until an admin moves them.
- Drawing codes are generated, never typed: `<PREFIX>-<NNN>` from the name (initials, numbers never reused, archived rows count), assigned in the create transaction under an advisory lock; the dialogs only preview them via `suggestDrawingCode`. Renaming keeps the code; a drawing moved to a project that already uses its code gets the next free one there.
- Revisions have a status lifecycle; `src/server/lib/revision-status.ts` `isRevisionImmutable` gates writes on locked revisions — use it before any line/section mutation.
- Revisions follow NAMING §6, for drawings and BOMs alike: **P01, P02…** until the client approves, **C01, C02…** from then on, never back to P (taking the approval back keeps C). BOM labels are stored as text in `bom_revision.letter` (column name kept; letters A, B… until 0030, numbers until 0034): render with `formatBomRevision()` (a bare number reads as P), pick the next with `nextBomRevision()` (C once the BOM has a C). `changeRevisionStatus` → Approved renames the revision to the next C, and a draft opened on top of it too.
- BOM statuses (`src/lib/bom-status.ts`, client-safe; the `revision_status` enum is built from `REVISION_STATUSES`): Draft → Committed by Commit, Committed → Sent to procurement (`review`) by `sendBomToProcurement`; only **Approved** (the client confirmed it) is set by hand — `changeRevisionStatus` (`{ ok, error }`, comment required, stamps `status_changed_by_id/_at` + `status_comment`, audits `bom.status.changed`), on the BOM's latest non-draft revision only (a newer draft doesn't block it). Taking the approval back returns to `committed`, or `review` once the revision was sent — "sent" means an `approval_workflow` row exists (`revisionSentSql`), never the status alone. An approved revision can still go to procurement once (`canSendToProcurement`) and stays Approved. `in-progress`/`locked` only come from the approval workflow. The `/builder` list filters like `/drawings`: status tabs + `BomFilterBar` (`components/boms/bom-filters.tsx`, URL params `q`, `project`, `owner`, `status`, `mine`, `outdated`).
- A BOM's owner (`bom.owner_id`) changes only together with a new revision: `branchRevision({ ownerId })` (the New revision / Clone dialog, `components/revisions/branch-revision-dialog.tsx`) stamps the new draft's `owner_id` and moves the BOM's in the same transaction — there is no other owner edit. Omitting `ownerId` keeps the current owner (the person branching doesn't take it over); a new owner must be an active non-viewer (`OWNER_NOT_ELIGIBLE`).
- BOM approvals (`src/server/actions/approvals.ts`, no UI yet — only `requestApproval` runs, via `sendBomToProcurement`): the requester can't approve, one person approves at most one stage, an assigned stage is only the assignee's, only the requester or an admin cancels and only while pending; stage moves are conditional updates in a transaction.
- Engineering drawings (`/drawings`; working files stay on the company file server — `drawing.file_location` is a free-text path there, e.g. `2026/BMW/CCTV`): `drawing` (per project, code unique among non-deleted) → `drawing_revision` (only the latest moves, older ones are locked; `number` 1, 2… is what "latest"/"newer"/"outdated" compare, the generated `label` column — P01… or C01… from `c_number` — is what people see: select it, never format the number. `c_number` is set by `writeStatusChange` when the revision first reaches Approved A/B or As Built and on every revision created after that. Transmittals and PDFs keep a `revision_label` snapshot of what they went out under) → `drawing_event` (created/updated/status/comment timeline). Status rules live in `src/lib/drawing-status.ts` `checkDrawingTransition`: statuses are free except that Awaiting approval and later require a second engineer (not the owner) to approve from Need to be approved. Whoever requests the approval can't name themselves as the reviewer, and `isOwnerChangeBlocked` stops the latest revision's reviewer/approver from becoming the owner — together they close "hand the drawing to someone else, approve it yourself". Status changes email the owner, approver and `drawing_notify_recipient` users (global rows have `project_id = null`) via `after()` in `src/server/lib/drawing-notify.ts`; drawing actions return `{ ok, error }` instead of throwing.
- Bulk edits on `/drawings` (editors only): `DrawingsRegister` (`components/drawings/drawings-register.tsx`) adds checkboxes and a sticky bar whose dialogs (`bulk-edit-dialogs.tsx`) change status, owner or due date of the ticked drawings — codes are not bulk-editable. `src/lib/drawing-bulk.ts` plans each change with the single-drawing rules (`checkDrawingTransition`, `isOwnerChangeBlocked`); the dialogs preview the plan and `bulkChangeDrawingStatus` / `bulkSetDrawingOwner` / `bulkSetDrawingDueDate` re-check it, save each drawing on its own (history event + audit row, `bulk: true` in the payload) and return `{ updated, skipped }` with a reason per skipped drawing. A bulk status change sends each follower one digest email (`notifyDrawingStatusChanges`) instead of one per drawing.
- Drawing PDFs (`drawing_file`, rules in `src/lib/drawing-files.ts`): one current PDF per revision, uploaded only by the drawing owner or an admin, only to the latest revision, and only once its status passes the admin-set gate (`system_settings.drawing_file_gate`: `approved` = Approved A/B/As Built by default, or `need-approval`). The browser posts straight to the bucket (presigned POST from `requestDrawingFileUpload`), then `confirmDrawingFileUpload` checks the stored bytes start with `%PDF-`. Keys are `drawings/<project>/<drawing>/<label>/<drawing>_<label>_<id>.pdf` (`<label>` = `P03`, `C01`…, stored on the row as `revision_label`; PDFs uploaded before the P/C change keep their `rev<n>` keys) and are never overwritten (Railway buckets have no versioning): replacing or removing a PDF archives the row and keeps the object. Everyone opens files through `/api/drawings/files/[id]` (access check, audit, 302 to a 5-minute presigned GET named `<code>_<label>.pdf`, e.g. `ELV-101_C01.pdf`); viewers only get PDFs of revisions that pass the gate, and transmittal emails/feeds link the PDF on the same terms. The DXF standard check lives in `services/dxf-checker` (see Integrations); the app side (#18 stage 2) isn't wired yet.
- BOM ↔ drawing references (`bom_revision_drawing`) store the drawing revision a BOM revision was built from. A reference is outdated only when a later drawing revision has `bom_impact = true` and is newer than both the built-from revision and `checked_revision_id` — use `isOutdatedSql` / `bomImpactRevisions` in `src/server/lib/bom-drawing-outdated.ts`, never a plain revision-number comparison. `confirmNoBomChange` ("No BOM change") records the check on the BOM's current revision even when it's committed — like the status change, a metadata write allowed on an immutable revision; lines and the built-from revision never change. Join `drawing_revision` more than once with `alias()` from `drizzle-orm/pg-core`, not `aliasedTable` (the row type collapses to `never`).

### My work (personal to-do)
- `/my-work` — reached from the top-bar bell (count on every page), the sidebar item and the dashboard's "Your work" strip (`components/my-work/`). Everything is derived live from domain rows, so there is nothing to tick off: a task leaves the list once it's done. Loader `src/server/queries/my-work.ts` (wrapped in React `cache`, so the layout's bell and the page/dashboard share one load per request); pure rules and wording in `src/lib/my-work.ts`.
- **To do:** latest drawing revisions in Need to be approved with the user as reviewer; unconfirmed transmittals of current revisions to them (`listMyPendingReceipts`); open remarks on drawings they own; BOMs they own whose current revision is outdated (`listOutdatedBomReferences({ ownerId })`). **Deadlines:** their open drawings due within 14 days (late ones included) and dates of projects they manage (`project.owner_id`, `listDeadlines({ ownerId })`) within 30. **Waiting on others:** their drawings in Need to be approved / Awaiting approval.
- **Updates** (last 30 days, never the user's own actions): events and remarks on drawings they're involved in (owner, reviewer of any revision, commented or raised a remark), their remarks resolved, revisions issued to them, BOM status changes on BOMs they own, and BOM handovers (`bom.revision.branched` audit rows with `previousOwnerId`). `my_work_seen` keeps the last visit (never visited = the last 7 days are new); `UpdatesFeed` calls `markMyWorkSeen` on open, which `refresh()`es the bell while the "New" tags stay for that visit. Bell = to do + overdue + new updates (`bellCount`). A new kind of task or update goes in both files and in the `my-work` Help section.

### Server actions vs. queries
- `src/server/actions/*` — `"use server"` mutations. Always: validate input with Zod → `requireSession()` (or `requireRole`) → mutate → `audit(...)` → `revalidatePath(...)`.
- `src/server/queries/*` — read-only data loaders called from server components.
- `src/server/audit.ts` writes to `auditLog` (with IP + user agent); call it after every mutation, including deletes. Auth events (sign-in, failed sign-in, password change/reset) are written from better-auth hooks in `src/lib/auth.ts` via `src/server/lib/audit-write.ts`, which must stay free of `server-only` because the seed scripts import `auth`. Security/admin kinds listed in `src/lib/audit-kinds.ts` `ADMIN_ONLY_KINDS` show only on `/audit` (admins); History → Activity shows the rest to everyone. New audit kinds need a label in `src/components/history/activity-table.tsx`.

### Client state
Zustand stores in `src/stores/` (`builder-store.ts`, `tweaks-store.ts`) hold ephemeral UI state only — filters, column visibility, etc. Persisted preferences use a versioned migration (see the `v2 migration` in recent commits). Don't put server data in stores; pass it down via server-component props or fetch via server actions.

### Integrations
- **better-auth** (`src/lib/auth.ts`): email/password only. Public sign-up is disabled; cookies are pinned to `httpOnly`, `sameSite=lax`, 7-day `maxAge`, and `secure` in production.
- **Excel exports are never stored.** BOM exports (`src/server/lib/run-export.ts`) record a `bom_export` metadata row and hand the bytes straight back; `api/exports/[id]/download` rebuilds the file from the revision + saved options (`renderExportFile`). Catalog/vendor/dashboard `.xlsx` routes stream too. Don't reintroduce S3 uploads for exports.
- **S3** (`src/lib/s3.ts`): drawing PDFs (`drawings/`) and catalog-import staging (`imports/`). Browser uploads need bucket CORS for the app origin — `scripts/s3-cors.mjs` sets it (local MinIO allows every origin and doesn't implement bucket CORS). Env: `AWS_REGION`, `S3_BUCKET`, optional `AWS_S3_ENDPOINT` + `S3_FORCE_PATH_STYLE` for MinIO/local.
- **exceljs / papaparse** (`src/lib/excel.ts`): catalog import + BOM export.
- **Env validation** (`src/lib/env.ts`): Zod-validated at module load — adding a new env var means updating this schema. `APP_VERSION` / `APP_REVISION` are baked into the image by the Docker build and reported by `/api/health`.
- **dxf-checker** (`services/dxf-checker/`, Python 3.13 + FastAPI + ezdxf, own README): a separate Railway service on the private network only (`dxf-checker.railway.internal:8080`) that checks one DXF against NAMING 0.0.3 / DRAFTING 0.0.5 and posts findings back (#18 stage 1). Stateless: every request carries the enabled rules and parameters. The app never calls it yet; when it does, the app writes the Remarks. The root `.dockerignore` keeps `services/` out of the app image. Tests: `python -m pytest` in that folder (CI runs them).

### UI conventions
- shadcn/ui primitives live in `src/components/ui/`; feature components are grouped by surface (`builder/`, `preview/`, `approvals/`, `master/`, etc.).
- Tailwind v4 with CSS variables (e.g. `bg-[var(--color-bg)]`); design tokens are defined in `src/app/globals.css`. The palette is defined twice there — light on `:root`, dark on `:root.dark` — and every other name (`--color-*`, the shadcn variables, the short names) points at it, so use tokens, never raw hex, or a theme breaks. Solid fills under white text use `--accent` / `--green-fill` / `--red-fill` (the plain semantic colors turn light in dark mode). The look is deliberately enterprise: one solid `--accent` blue (no gradients or glows), radii `--r-1…4` = 2/4/6/8px, shadcn `--radius` 4px, square status tags.
- **Theme:** light / dark / system lives in `src/lib/theme.ts` (localStorage `theme` → `dark` class + `color-scheme` + `theme-color` meta on `<html>`); the inline script in `app/layout.tsx` applies the same rules before paint — keep them in step. Pickers: `ThemeToggle` (account menu) and `ThemeButton` (top bar) in `components/shell/theme-toggle.tsx`; the Toaster follows `useTheme()` from there (there is no next-themes provider). shadcn's own "accent" is not the brand `--accent`: menu/select hover uses `bg-muted`.
- **Brand:** the app is **Revline** (formerly BOM Studio). Name, raw icon colours and the mark (an R whose leg runs into a line, one path on a 64 grid) live in `src/lib/brand.ts`; `<LogoMark>` (`components/brand/logo-mark.tsx`) draws it in-app with `--accent`/`--on-accent`. `apple-icon.tsx` and `/pwa-icon` render it on request; `src/app/icon.svg` and `favicon.ico` are static — rerun `npx tsx scripts/brand-icons.ts` after changing the mark (`tests/unit/lib/brand.test.ts` checks they match, and that `public/offline.html` carries the same path).
- **Mobile first.** The layout layer at the end of `globals.css` is written phone-first: base rules are the phone layout, `min-width: 701px` adds tablet, `min-width: 961px` desktop (sidebar becomes a drawer + bottom tab bar below 961/701px). Every page must fit a 360px phone with no horizontal page scroll. For per-element tweaks use `max-[701px]:` (below 701px) / `min-[701px]:` utilities; phone-only CSS uses `max-width: 700.98px` so the boundary matches.
- Tables on phones: add `tbl-list` (compact rows — cell classes `l-title`, `l-aside`, `l-line`, `l-meta`, `l-end`, `l-hide`) or `tbl-cards` (label/value cards — `data-label` on each `<td>`, plus `td-main`, `td-full`, `td-end`, `td-hide`; `cards-4` for numeric tables). See `drawings-table.tsx` / `dashboard-parts.tsx`.
- Detail pages pass `back={{ href, label }}` to `PageHead` ("← Drawings" above the title, `components/master/back-link.tsx`): it always lands on the page it names, stepping back through history when that is the previous page (`src/lib/nav-history.ts`, recorded by `ShellChrome`) so lists keep their filters. Single-column pages (Settings) sit in a centred `.page-narrow` column.
- `PageHead` actions (`.page-actions`) fill the row on phones; `.tabs-scroll` makes a tab row scroll sideways on phones; collapsible filters use `.filters-bar` / `.filters-toggle` / `.filters-panel` / `.chip-toggle` (see `drawing-filters.tsx`). shadcn `DialogContent` is a bottom sheet on phones with a sticky footer. Touch targets grow on coarse pointers globally.
- **Toasts:** import `toast` from `@/lib/toast`, never from `sonner` (ESLint blocks it). Success closes on its own; error, warning and info stay until the user closes them (close button top-right; the same text replaces an open toast instead of stacking). Green/yellow/red come from the `--toast-*` tokens in `globals.css`.
- **In-app help:** `/help` (`src/app/(app)/help/page.tsx`, content in `src/components/help/help-sections.tsx`, filtered by role) plus `<HelpTip topic="…">` (?) popovers whose short text lives in `src/lib/help-topics.ts`. Every topic id is also a section anchor on `/help` (`tests/unit/lib/help-topics.test.tsx` checks it). When a rule changes — statuses, roles, what locks what — update the tip and the section with it. Say why a control is disabled or read-only in a visible `<BlockedNote>` next to it, not a `title` tooltip (phones never show those).
- Turbopack dev keeps serving the old compiled `globals.css` after edits (even across restarts); delete `.next/dev` and restart `npm run dev` to see CSS changes.

## Tests
- Unit: `tests/unit/**/*.test.{ts,tsx}` and colocated `src/**/*.test.{ts,tsx}`. `tests/setup.ts` loads `@testing-library/jest-dom`. Vitest aliases `server-only` to `tests/test-helpers/server-only-shim.ts` so server modules can be imported in jsdom.
- **Server tests TRUNCATE every table** (`tests/test-helpers/db.ts` `resetDb`) in whatever `DATABASE_URL` points at, and Vitest loads `.env.local` (the dev DB). Run them against a throwaway DB instead — dotenv doesn't override an already-set variable: `docker exec bom-postgres psql -U bom -d bom -c "create database bom_test"` once, then `DATABASE_URL=postgres://bom:<pw>@localhost:5432/bom_test npx drizzle-kit migrate` and `DATABASE_URL=… npx vitest run`.
- E2E: `tests/e2e/*.spec.ts` against the real dev server (Playwright auto-launches `npm run dev`); helpers in `tests/e2e/helpers.ts`. CI doesn't run them; run them locally before a release that changes the flows they cover.

## CI/CD and releases
- **CI** (`.github/workflows/ci.yml`, every pull request and push to `main`): `npm run lint`, `tsc --noEmit`, `scripts/migrate.mjs` + `vitest run` against a throwaway Postgres 18 service (no `.env.local` there: the job sets placeholder env), the dxf-checker pytest suite, then both Docker images (`images.yml`). Pull requests only build the images; `main` pushes them as `main` and `sha-<short>`. Keep it green: a red `main` blocks the next release.
- **Images** (GHCR, public like the repo): `ghcr.io/tshamugia/bom` (root `Dockerfile`) and `ghcr.io/tshamugia/bom-dxf-checker` (`services/dxf-checker/Dockerfile`). They are built once in Actions with placeholder build env and carry no secrets; the runtime config is the Railway service variables. Never add secret `ARG`s to a Dockerfile.
- **Release:** bump the version in a PR (`npm version 0.1.3 --no-git-tag-version`), merge, then tag `main` with an annotated tag whose subject is the release title: `git tag -a v0.1.3 -m "v0.1.3 — <title>" -m "<notes>"` and `git push origin v0.1.3`. `release.yml` checks the tag against `package.json`, reruns CI, pushes `0.1.3`, `0.1` and `latest`, deploys, and only then creates the GitHub release (tag message + generated notes).
- **Deploy** (`deploy.yml`, called by the release or run by hand with a version to roll back): `scripts/railway-deploy.mjs` points the Railway services `dxf-checker`, then `bom`, at the image tag through the Railway API and waits for each deployment, then polls `$APP_URL/api/health` until it reports the version. Needs the `RAILWAY_TOKEN` secret (a Railway project token for production) and the `APP_URL` variable. Railway runs the services from GHCR images, so pushing to `main` doesn't deploy anything.
- **Migrations** run when the container starts (`node scripts/migrate.mjs && node server.js`), before the new deployment takes traffic. Rolling back to an older image does not undo them, so back up Postgres in Railway (Postgres → Backups) before releasing migrations that rewrite data.
- `/api/health` is public (not in `src/proxy.ts`): `{ ok, version, revision }`, 503 when Postgres doesn't answer. Railway's deploy healthcheck uses it.
