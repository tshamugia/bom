# Remove pricing and stock from the system

**Date:** 2026-05-05
**Branch (target):** `feat/bom-versioning` (current) — single commit on this branch

## Summary

Remove the `unit_price`, `on_hand`, and `stock_state` concepts from `item`, drop the snapshotted `unit_price_snapshot` on `bom_line`, and strip every UI/server/export surface that consumed them. Regenerate the catalog import template Excel so the download link in **Catalog → Import** delivers a 7-column file (no `unit_price`, `on_hand`, `stock_state`).

After this change, BOMs are quantity-only. There are no totals, no subtotals, no taxes, and no stock alerts anywhere in the app.

## Non-goals

- Re-introducing pricing later via a separate model (e.g., per-vendor cost). Out of scope.
- Migrating data from removed columns into a side-table. They are dropped outright.
- Backwards-compatible read paths for legacy `bom_export.options` jsonb. Old rows are read leniently — extra keys are ignored, missing keys default to `false`.

## Resolved open questions

These were flagged during brainstorming and now have decisions:

1. **Legacy `bom_export.options` jsonb:** Keys like `unitPrice/total/stock` linger on existing rows; the new typed `ExportColumnKey` no longer includes them and they're ignored on read. No data migration.
2. **Dashboard tile slot:** "Open value" is removed; the dashboard switches to a 3-tile layout (`Active BOMs`, `Avg. lead time`, `Approvals pending`). The `grid-cols-4` class becomes `grid-cols-3`.
3. **`bad_enum` row-error reason:** It was only emitted for `stock_state` parsing. After removal there are no producers, so it is deleted from the `RowErrorReason` union and from any switch/labels that reference it.
4. **Re-seeding:** `db/seed.ts` already truncates `bom_line, bom_revision, project, item, ...` cascade. After migrate + seed, the dev DB is consistent. No data preservation.

## Architecture overview

```
┌──────────┐   ┌──────────┐   ┌─────────┐
│  item    │   │ bom_line │   │ exports │
│ - sku    │   │ - qty    │   │ jsonb   │
│ - desc   │   │ - *snap* │   │ options │
│ - mfr    │   │ - sec    │   │ (legacy │
│ - unit   │   │ - pos    │   │ keys ok)│
│ ─────────│   │──────────│   └─────────┘
│ unit_price ❌│   │ unit_price_snapshot ❌│
│ on_hand    ❌│   └──────────┘
│ stock_state❌│
└──────────┘
```

The schema becomes strictly narrower. The migration drops 4 columns and 1 enum.

## Risk / blast radius

- **Build breaks until the cascade completes.** The change touches ~40 files; the migration must be generated and applied before the dev server can run because the schema-typed selects break at compile time. Plan to make the schema + types + server + UI edits atomically before running the app.
- **Existing `bom_export` rows** remain queryable (they only reference `revisionId`, `fileKey`, etc. — none of the dropped columns). Their `options` jsonb has stale keys; harmless.
- **Persisted zustand state** in users' browsers contains old `tweaks-store` keys (`price`, `total`, `stock`). The store key (`bom-tweaks`) keeps them as ignored extras; no version bump needed. If we wanted strict cleanup, bump the persist `version` — not in scope.
- **Drizzle-kit ordering**: enum drop must come after all column references to it are gone. drizzle-kit usually orders this correctly; if not, hand-edit the generated SQL.

## Out of scope

- Replacement pricing model (per-vendor cost, BOM-level overrides, etc.).
- Adjusting any cron/automation/audit-log records that mention prices in `payload` jsonb (those are immutable history; they keep their old keys).
- Cleaning up the persisted browser state for users with old `tweaks-store` snapshots.
